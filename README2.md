# 주식 자동 매매 프로그램 ver1.1 패치노트

## 작업 개요

이번 작업에서는 키움증권 REST API 모의투자 기준으로 자동매매 프로그램의 기본 골격을 실제 동작 가능한 수준까지 연결하였고, 이후 운영 중 발생한 문제를 수정하면서 **실제 조회, 주문, 로그 기록이 정상적으로 동작하는 상태**까지 정리하였습니다.

이번 버전의 핵심 목표는 다음과 같았습니다.

* 키움증권 모의투자 REST API 연동
* 계좌 조회 / 현재가 조회 / 주문 기능 검증
* 자동매매 루프 실행 확인
* 동일 종목 재진입 허용 구조 반영
* API 호출 제한(429) 대응
* 사람이 읽기 쉬운 전략 로그 개선
* 이후 장세 분류 기반 전략 선택 구조로 확장 가능한 기반 마련

---

## 1. 개발 방향 변경

초기에는 한국투자증권 기준 구조로 시작하였으나, 이후 방향을 **키움증권 모의투자 버전**으로 변경하였습니다.

### 변경 사유

* 사용자님의 실제 사용 환경이 키움증권 중심으로 맞춰져 있었습니다.
* 키움 모의투자 계정 및 API 사용 준비가 완료된 상태였습니다.
* Python으로 REST API를 먼저 검증한 뒤 점진적으로 기능을 확장하기에 적합하였습니다.
* 장기적으로 자바 이식을 고려하더라도 현재 구조를 유지하면서 전략만 발전시키는 방향이 가능하였습니다.

## 2. 프로젝트 구조 정비

프로젝트는 자바 이식을 염두에 두고 역할별로 레이어를 나누는 구조를 유지하였습니다.

### 주요 구조

* `app/main.py`

  * 프로그램 진입점
* `config/`

  * 설정 파일 및 환경변수 로드
* `domain/`

  * 전략, 리스크, 서비스 로직
* `infra/broker/`

  * 키움 REST API 연동
* `infra/storage/`

  * 로그 및 상태 저장
* `tests/`

  * 기본 테스트 코드

### 설계 원칙

* 전략 판단과 브로커 연동 코드를 분리하였습니다.
* 설정은 외부 YAML과 `.env`로 관리하도록 하였습니다.
* 브로커 구현체를 바꾸더라도 서비스 로직은 최대한 유지되도록 구성하였습니다.
* 나중에 자바로 이식하기 쉽도록 책임을 명확히 분리하였습니다.

## 4. 환경 설정 관련 문제와 해결

### 문제 1. Python 실행 환경 혼선

초기에는 Python 설치 여부와 가상환경 활성화 과정에서 혼선이 있었습니다.

#### 원인

* Windows 환경에서 `python` 명령 인식 상태가 불명확했습니다.
* `venv` 활성화 경로 입력 과정에서 오타가 있었습니다.
* CMD와 VS Code 터미널을 오가면서 실행 위치가 섞였습니다.

#### 해결

* Python 설치 여부를 다시 확인하였습니다.
* VS Code 터미널 기준으로 작업 폴더를 통일하였습니다.
* 처음에는 가상환경 없이도 테스트를 진행할 수 있도록 안내드렸습니다.
* 이후 `.venv` 환경에서 패키지 설치 및 실행 방식으로 정리하였습니다.

### 문제 2. `.env.example`만 있고 실제 `.env`가 없어 인증 실패

#### 원인

* 프로그램은 `.env` 파일만 읽도록 되어 있었습니다.
* `.env.example`은 예시 파일일 뿐 실제 값은 로드되지 않았습니다.

#### 해결

* `.env.example` 내용을 참고하여 프로젝트 루트에 `.env` 파일을 생성하였습니다.
* 아래 값을 실제 모의투자 계정 값으로 입력하였습니다.

```env
KIWOOM_APP_KEY=...
KIWOOM_SECRET_KEY=...
KIWOOM_ACCOUNT_NUMBER=...
```

## 7. 주문 관련 문제와 해결

### 문제 6. 주문 시 계좌 유형 오류

#### 증상

모의투자 매수 주문 시 다음과 같은 응답이 발생하였습니다.

* 개인공매도이수전용 계좌라는 메시지
* 주문 불가

#### 원인

* 현재 토큰에 연결된 계좌가 일반 모의투자용 주문 계좌가 아니었습니다.

#### 해결

* 주문 가능한 일반 모의투자 계좌 기준으로 다시 연결 상태를 점검하였습니다.
* 이후 동일 주문 API에서 정상적으로 매수 주문이 접수되는 것을 확인하였습니다.

---

### 문제 7. 매도 주문 시 장 종료 오류

#### 증상

매도 주문 요청 시 `모의투자 장종료` 오류가 발생하였습니다.

#### 원인

* 주문 API는 정상 호출되었지만, 장이 종료된 상태라 키움 서버가 주문을 거절하였습니다.

#### 해결

* 이것은 코드 오류가 아니라 정상적인 서버 응답임을 확인하였습니다.
* 즉, 주문 API 연동 자체는 성공하였고, 장 상태에 따라 정상 거절된 것으로 판단하였습니다.

## 8. 전략 로직 확인

현재 기본 전략은 **단순 돌파 + 익절/손절 전략**입니다.

### 진입 조건

* 비보유 상태일 때
* 기준가 대비 일정 비율 이상 상승 시 매수

### 청산 조건

* 보유 상태일 때
* 평균단가 대비 익절 목표 도달 시 매도
* 평균단가 대비 손절 기준 이탈 시 매도
* 장 마감 전 강제 청산

### 특징

* 구조가 단순하여 디버깅이 쉽습니다.
* 주문 흐름 검증용 전략으로 적합합니다.
* 다만 시장 상황(상승/횡보/하락)을 구분하지 않는다는 한계가 있습니다.

## 9. 재진입 허용 구조 반영

### 문제 8. 한 번 매도한 종목을 다시 매수하지 않는 현상

#### 원인 후보

처음에는 동일 종목 하루 1회 진입 제한으로 의심하였으나, 실제로는 **잔고 캐시가 매도 후에도 유지되어 여전히 보유 중인 것으로 판단되는 문제** 가능성이 높았습니다.

#### 확인 내용

`RiskManager` 자체는 다음 설정값을 정상적으로 반영하고 있었습니다.

```yaml
allow_multiple_entries_per_symbol_per_day: true
```

즉, 동일 종목 재진입 자체를 막는 구조는 아니었습니다.

#### 실제 원인

* 매수/매도 주문 성공 후에도 `cached_balance`가 남아 있었습니다.
* 그 결과 다음 루프에서 프로그램이 예전 잔고를 보고 “아직 보유 중”이라고 판단할 수 있었습니다.

#### 해결

* `_try_buy()`와 `_try_sell()`에서 주문 성공 시 잔고 캐시를 무효화하도록 수정하였습니다.

```python
self.cached_balance = None
self.cached_balance_loaded_at = None
```

이후 다음 루프에서 최신 잔고를 다시 읽도록 하였습니다.

## 10. 키움 REST API 호출 제한(429) 문제와 대응

### 문제 9. `ka10001` 현재가 조회 API에서 429 발생

#### 증상

다음과 같은 오류가 반복적으로 발생하였습니다.

* `허용된 요청 개수를 초과하였습니다`
* `API ID=ka10001`
* HTTP 429

#### 원인

* 현재가 조회를 루프마다 직접 호출하는 구조였습니다.
* 키움 REST API의 현재가 조회 제한이 예상보다 엄격하였습니다.
* 이전 수동 테스트 호출량과 자동매매 루프 호출이 누적되었을 가능성도 있었습니다.

#### 1차 대응

* `poll_interval_seconds`를 증가시켰습니다.
* 429 발생 시 180초 backoff 하도록 `main.py` 예외 처리 로직을 추가하였습니다.

#### 한계

* 180초 대기 후에도 즉시 재시도하면 다시 429가 발생하는 경우가 있었습니다.
* 단순 반복 주기 조절만으로는 안정적이지 않았습니다.

## 11. 계좌 조회/현재가 조회 캐시 구조 도입

429 문제를 줄이기 위해 `TradingService`에 캐시 구조를 도입하였습니다.

### 추가한 캐시

* `cached_balance`
* `cached_balance_loaded_at`
* `cached_market_prices`
* `cached_market_price_loaded_at`

### 적용 방식

* 계좌 조회는 일정 시간 동안 캐시 재사용
* 종목 현재가도 일정 시간 동안 캐시 재사용
* 메인 루프는 계속 돌되, 실제 API 호출은 줄이는 구조로 변경

### 관련 설정 추가

```yaml
trading:
  poll_interval_seconds: 5
  balance_refresh_seconds: 180
  price_refresh_seconds: 120
```

### 효과

* 계좌 조회와 현재가 조회를 매 루프마다 직접 호출하지 않게 되었습니다.
* API 제한에 대응할 수 있는 기반이 마련되었습니다.

## 12. 캐시 적용 중 발생한 문제와 해결

### 문제 10. `TradingConfig` 필드 부족 오류

#### 증상

`TradingConfig.__init__()`에서 필수 인자 누락 오류가 발생하였습니다.

#### 원인

* `balance_refresh_seconds`, `price_refresh_seconds`를 추가하면서
* 기존 `trading:` 설정 항목 일부가 YAML에서 빠졌습니다.

#### 해결

`settings.yaml`의 `trading:` 블록을 전체 항목이 포함되도록 복구하였습니다.

```yaml
trading:
  poll_interval_seconds: 5
  balance_refresh_seconds: 180
  price_refresh_seconds: 120
  order_cash_per_trade: 200000
  max_positions: 2
  allow_multiple_entries_per_symbol_per_day: true
  force_exit_before_market_close_minutes: 10
```

---

### 문제 11. `error_message` 관련 예외 처리 코드 오류

#### 증상

`UnboundLocalError: cannot access local variable 'error_message'` 발생

#### 원인

* `error_message = str(exc)`를 만들기 전에
* `if "http=429" in error_message ...`를 먼저 검사하였습니다.

#### 해결

* `except Exception as exc:` 블록에서 먼저 `error_message = str(exc)`를 만든 뒤
* 그 다음 429 여부를 판단하도록 순서를 수정하였습니다.

---

### 문제 12. `TradingService`에 `run_once`가 없다는 오류

#### 증상

`AttributeError: 'TradingService' object has no attribute 'run_once'`

#### 원인

* 복사/붙여넣기 과정에서 `run_once()` 함수의 들여쓰기가 깨졌습니다.
* `run_once()`가 클래스 바깥으로 빠졌거나 메서드 레벨이 무너졌습니다.

#### 해결

* `TradingService` 파일 전체를 다시 정리하여 통째로 교체하였습니다.
* 이후 클래스 내부 메서드 구조가 정상화되었습니다.

## 13. 로그 개선

초기 로그는 다음과 같은 단순한 형태였습니다.

* `signal generated`
* `buy blocked`
* `account balance loaded`

이 방식은 동작 여부는 확인 가능했지만, 실제 운영 시 **왜 샀는지 / 왜 안 샀는지 / 왜 홀딩 중인지** 파악하기 어려웠습니다.

### 개선 내용

* HOLD / BUY / SELL 판단 로그를 사람이 읽기 쉬운 자연어로 변경
* 주문 성공/실패 로그를 별도로 명확하게 분리
* 캐시에서 읽은 경우와 API에서 직접 읽은 경우를 구분하여 출력

### 개선 후 예시

* `[HOLD] 005930 | 현재가 222,250원 | 돌파 기준 미도달`
* `[BUY ] 001510 | 현재가 6,180원 | 돌파 조건 충족`
* `[ORDER] 001510 | 매수 주문 접수 완료 | 수량 45주 | 주문번호 ...`

# 주식 자동 매매 프로그램 ver1.2 패치노트

## 작업 개요

이번 작업에서는 ver1.1에서 구축한 기본 자동매매 루프 위에 **장세 분류 기반 전략 선택 구조**를 도입하고, 실제 운영 중 발견된 핑퐁 매매 문제를 해결하였습니다. 또한 키움증권 WebSocket API를 활용한 조건검색 연동 구조를 추가하여 종목을 자동으로 편입/편출할 수 있는 기반을 마련하였습니다.

이번 버전의 핵심 목표는 다음과 같았습니다.

* 장세 분류기 도입 (MA + RSI + MACD + 거래량 + RSI 방향)
* 장세별 전략 자동 선택 구조 구현
* 3중 필터 매수 조건 적용 (엑셀 황금시간 조건 기반)
* 핑퐁 매매 차단 (재진입 쿨다운)
* 조건검색 WebSocket 연동
* 일일 리포트 자동 생성

## 1. 장세 분류기 도입

### 배경

ver1.1의 전략은 단순 돌파 전략으로, 시장이 하락 중이어도 기준가 대비 1% 이상 오르면 무조건 매수하는 구조였습니다. 장세를 구분하지 못하는 것이 가장 큰 한계였습니다.

### 구현 내용

`domain/market_regime/classifier.py`를 신규 생성하였습니다.

일봉 데이터(ka10081)를 기반으로 4가지 지표를 조합하여 장세를 판단합니다.

**1단계 (초기 구현)**
- 이동평균 골든/데드크로스 (5일선 vs 20일선)
- RSI 수치 기반 과매수/과매도 판단

**2단계 (고도화)**
- MACD 골든/데드크로스 추가 (macd_fast=12, macd_slow=26, macd_signal=9)
- 거래량 급증 여부 추가 (20일 평균 대비 1.5배 이상)

**3단계 (정밀화)**
- RSI 방향 판단 추가 (↑상승 / ↓하락 / →보합)
- RSI 30 이하라도 하락 중이면 매수 차단

### 장세 분류 결과

| 장세 | 조건 | 적용 전략 |
|---|---|---|
| BULLISH | MA 상승 + RSI 정상 + MACD 골든크로스 | 3중 필터 매수 전략 |
| SIDEWAYS | 위 조건 미충족 | 신규 매수 차단, 보유분만 관리 |
| BEARISH | MA 하락 + RSI 정상 + MACD 데드크로스 | 신규 매수 차단, 손절 우선 |
| UNKNOWN | 데이터 부족 | 보수적 관망 |

### 관련 설정 추가

```yaml
market_regime:
  short_ma_days: 5
  long_ma_days: 20
  history_days: 60
  rsi_period: 14
  rsi_overbought: 80.0
  rsi_oversold: 20.0
  history_refresh_seconds: 3600
  macd_fast: 12
  macd_slow: 26
  macd_signal: 9
  volume_surge_ratio: 1.5
```

## 2. 전략 라우터 및 보조 전략 추가

### 구현 내용

장세 분류 결과에 따라 전략을 자동으로 선택하는 구조를 도입하였습니다.

**추가된 파일**
- `domain/strategy/strategy_router.py` — 장세별 전략 선택
- `domain/strategy/hold_strategy.py` — 횡보/하락장 관망 전략

### 라우팅 규칙

```
BULLISH  → BreakoutStrategy (3중 필터 매수 전략)
SIDEWAYS → HoldStrategy     (신규 매수 없음, 보유분만 익절/손절)
BEARISH  → HoldStrategy     (동일, 로그에 '하락장' 표시)
UNKNOWN  → HoldStrategy     (보수적 관망)
```

### 설계 원칙

나중에 전략을 추가하거나 변경할 때 `strategy_router.py`만 수정하면 됩니다. `TradingService`나 다른 파일은 건드릴 필요가 없습니다.

## 3. 3중 필터 매수 전략 적용

### 배경

사용자가 제공한 엑셀 자료(기술치수에 의해 매매시기 조사)의 황금시간 조건을 코드로 구현하였습니다.

### 황금시간 매수 조건

```
① RSI 30 이하 + 상승 중(↑)   → 바닥 찍고 반등 시작
② MACD 골든크로스             → 상승 모멘텀 시작
③ 거래량 급증                 → 세력 유입 확인

3개 충족 → [BUY] 황금시간 3중 조건 모두 충족
2개 충족 → [BUY] 3중 조건 중 2개 충족 (보수적 진입)
1개 이하 → [HOLD] 매수 조건 N/3 충족
```

### RSI 방향 판단 추가

RSI 수치만으로는 부족하다는 점을 보완하였습니다.

```
RSI 28 + 하락 중(↓) → 아직 바닥 아님, 더 내려갈 수 있음 → HOLD
RSI 28 + 상승 중(↑) → 바닥 찍고 반등 시작 → 매수 조건 충족
```

### 추가 매도 조건

기존 익절/손절 외에 고점 반전 감지 조건을 추가하였습니다.

```
RSI 70 이상 + MACD 데드크로스 → 조기 차익 실현
```

## 4. 일봉 데이터 조회 API 연동

### 문제

장세 분류기가 이동평균, RSI, MACD를 계산하려면 일봉 히스토리 데이터가 필요하였습니다.

### 해결

키움 일봉 차트 조회 API(ka10081)를 연동하였습니다.

#### API 스펙 확인 과정

처음에 ka10086으로 잘못 구현하였다가 실제 키움 문서를 확인하여 ka10081로 수정하였습니다.

| 항목 | 수정 전 (잘못됨) | 수정 후 (정상) |
|---|---|---|
| API ID | ka10086 | ka10081 |
| endpoint | /api/dostk/stkinfo | /api/dostk/chart |
| 파라미터 | strt_dt, end_dt | base_dt, upd_stkpc_tp |
| 응답 배열 키 | stk_dt_pole_qry | stk_dt_pole_chart_qry |
| 종가 필드 | cls_pric | cur_prc |

### 일봉 캐시 구조

일봉 데이터는 매 루프마다 조회하지 않고 1시간마다 한 번만 갱신하도록 캐시 구조를 도입하였습니다.

```python
cached_daily_bars: dict[str, list]
cached_daily_bars_loaded_at: dict[str, datetime]
```

## 5. API 호출 429 문제 추가 대응

### 문제

장세 분류기 도입으로 프로그램 시작 시 종목당 ka10001(현재가) + ka10081(일봉) 두 개의 API가 동시에 호출되면서 429가 더 자주 발생하였습니다.

### 해결

두 가지 방법을 동시에 적용하였습니다.

**종목 간 딜레이 추가**

```python
if i > 0:
    time.sleep(1.0)  # 두 번째 종목부터 1초 대기
```

**호출 순서 최적화**

일봉(장세) 먼저 조회 후 현재가 조회 순서로 변경하였습니다. 일봉은 캐시가 적용되어 있어 첫 실행 이후에는 API 호출이 없습니다.

**poll_interval 조정**

```yaml
poll_interval_seconds: 10  # 5초 → 10초
```

## 6. 핑퐁 매매 차단

### 문제

실제 거래 로그(`trades.csv`)를 분석한 결과, 매도 직후 5초 만에 같은 종목을 재매수하는 핑퐁 패턴이 반복되고 있었습니다.

```
14:42:14  SELL 36주
14:42:19  BUY  37주  ← 5초 뒤 재매수
14:52:15  SELL 37주
14:52:20  BUY  36주  ← 또 재매수
```

### 원인

`allow_multiple_entries_per_symbol_per_day: true` 설정과 단순 돌파 전략의 조합으로, 매도 후에도 돌파 조건이 유지되면 즉시 재매수가 발생하였습니다.

### 해결

매도 후 일정 시간 동안 같은 종목 재매수를 차단하는 쿨다운 구조를 도입하였습니다.

```python
# _try_buy() 진입 시 쿨다운 체크
last_sold_at = self.state.last_sold_at_by_symbol.get(symbol)
if elapsed < cooldown_sec:
    [COOL] 001510 | 재진입 쿨다운 중 (299초 남음)
    return

# _try_sell() 성공 시 시각 기록
self.state.last_sold_at_by_symbol[symbol] = datetime.now().isoformat()
```

### 관련 설정 추가

```yaml
trading:
  reentry_cooldown_seconds: 600  # 매도 후 10분간 재매수 차단
```

## 7. 조건검색 WebSocket 연동

### 배경

현재는 `settings.yaml`에 종목을 수동으로 등록하는 방식입니다. 영웅문(HTS)에서 조건검색식을 만들어두면 조건을 충족하는 종목을 자동으로 감지할 수 있습니다.

### 구현 내용

**추가된 파일**
- `infra/websocket/kiwoom_ws.py` — WebSocket 연결/로그인/PING/재연결
- `infra/websocket/condition_watcher.py` — 조건검색 구독, 편입/편출 처리
- `infra/websocket/real_token.py` — 실전 계좌 전용 토큰 발급

### 동작 흐름

```
1. 실전 계좌로 WebSocket 로그인
2. CNSRLST → 저장된 조건검색식 목록 조회
3. CNSRREQ(search_type=1) → 실시간 구독 시작
4. REAL 메시지 수신
   843=I → targets에 종목 자동 추가 (편입)
   843=D → targets에서 종목 자동 제거 (편출)
5. 종료 시 CNSRCLR → 구독 해제
```

### 이중 계좌 구조

모의투자 환경에서는 조건검색 WebSocket이 지원되지 않습니다. 이를 해결하기 위해 다음 구조를 적용하였습니다.

```
실전 계좌 (WebSocket)     →    조건검색 종목 수신
모의 계좌 (REST API)      →    실제 주문 실행
```

### 관련 설정 추가

```yaml
websocket:
  enabled: true
  url: wss://api.kiwoom.com:10000/api/dostk/websocket
  condition_seq: 0      # HTS에서 저장한 조건식 번호
  max_symbols: 5
  app_key: ${KIWOOM_REAL_APP_KEY}
  secret_key: ${KIWOOM_REAL_SECRET_KEY}
```

### main.py 비동기 전환

WebSocket 루프와 REST 루프를 동시에 실행하기 위해 `main.py`를 `asyncio` 기반으로 전환하였습니다.

```python
await asyncio.gather(
    trading_loop(...),   # REST API 매매 루프
    watcher.start(),     # WebSocket 조건검색 루프
)
```
